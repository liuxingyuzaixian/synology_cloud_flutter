NasFlow 首页改版方案（设计图 v2，26.10.31 修订）

保留我们已有的能力（下拉刷新、传输入口、可配置宫格、频率滑块、玻璃底栏），把首页从「信息挤在一张卡里」改成 顶栏身份区 + 双信息卡 + 蓝色调快捷宫格 + 五张实时卡的纵向流。所有模块的数据来源都是本项目里已经在调的 DSM 接口， 不引入新依赖；未核实的字段在下面的表格里单独标出。

v2 改了三处：① 顶栏不放型号，型号进「设备信息卡」（已定）；② 宫格与底栏功能重复照放（已定）； ③ 新增深色模式两屏（⑤⑥，已定同期做）。守护判定从「按秒」改成按轮询次数，报警通知上多了四个「忽略」按钮（第 ③④ 屏）。

进程处置这条能力怎么落地
  • 这是唯一会改变 NAS 运行状态的动作，比报警本身危险，所以整页的设计前提是先设护栏再谈交互。
  • 单选（你要求不做多选）：右侧圆点选中后底部两颗按钮才亮；关键服务行置灰虚线圈，点不动。
  • 「暂停」放在「杀掉」前面且默认引导用它：SIGSTOP 能立刻止血、可撤销， 而且把内存和已打开的文件描述符留在原地——上次那种事件里这就是取证材料。
  • 确认层要的信息一条都不能少：PID、属主、完整命令行、它现在的读写贡献、停掉会影响什么， 再手动输入 PID 后三位。只点一下「确定」不算二次确认。
  • 被 DSM 守护的进程杀了会复活（servinfo / synoscgi 那类），文案必须提前讲清楚， 否则用户以为「杀不掉 = 功能坏了」。这类目标请改用「停所属套件」（方案 §7.2 路线 B，接口现成）。
  • 处置完 3 秒回采一次进程表，把结果如实显示。「已进入停止状态」的字段依据还没实测过 （现有 Process list 我们只用到 pid/名字/CPU/内存）， 拿不到状态字段时这里只能写「疑似已暂停」，不装成确定。
  • 报警通知栏不带处置按钮，只有忽略四档；处置只在 App 内、登录后、过了应用锁才可用。
  • 实现路线与代价（含「为什么不走 SSH」）见 docs/磁盘异常读写守护方案.md §7： 现实做法是 NAS 侧预建一条 root 任务 + App 写一行受校验的指令文件，需要一次性授权。
