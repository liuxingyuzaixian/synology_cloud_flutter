## 0. 已经定死的事（26.10.31 两轮答复汇总）

1. **判定跟着轮询次数走，不跟秒走**。守护不再有自己独立的 2 秒定时器，
   样本周期 = 首页「设备监控」滑块选的档位；连续 **2 个越线样本**才报。
   30 秒档 ⇒ 最快 30 秒、最坏约 1 分钟判定出来（你说的那个口径）。
2. **忽略 = 真停轮询**。点「忽略 15 分钟」之后守护一个请求都不发，
   到点自动恢复；期间不判定、也不报「失联」。
3. **阈值默认 40 MB/s，但可以调**，往上往下都要给口子（见 §4）。
4. **常驻通知不设独立开关**：它跟着「开启守护」这一个开关走。
   不接受通知栏长期一条通知，那就别开守护——不用再加一个选项把状态搞复杂。
5. **新增诉求：手机侧直接处置可疑进程**（暂停 / 杀掉，单选，不做多选）。
   可行性调研见 §7，结论是能做，但要按路线走，不是点一下那么轻。

6. **【26.11.01 反馈第 1 条，已覆盖 §1.4】「失联」和「恢复采样」两类事件全部删除**。
   网络本身会误报（切换 Wi-Fi/流量、NAS 短暂不可达都会连续失败），而守护真正要说的是
   **取到的数据有没有异常**。所以取不到数不再产生任何通知与消息中心记录，
   失败计数（`missedStreak`）只留在日志里当排障线索；本机已落盘的旧记录
   读取时按 `DiskWatchService.retiredEventKinds` 过滤掉，不改动 prefs 里的原始 JSON
   （万一要回滚，数据还在）。

## 1. 信号与判定

### 1.1 数据来源（本项目已在调用）

`SYNO.Core.System.Utilization`（`method:get`、`type:current`）返回的 `data.disk.total` 节点。
封装在 `lib/network/dsm_api.dart`，**两个方法别写成一个名字**（早先这里写的
`systemUtilization` 不存在，是笔误）：

| 方法 | resource | 谁在用 |
| --- | --- | --- |
| `utilization({resource: ...})` | 六段全拉（cpu/memory/network/lun/space/disk） | 资源监控页 |
| `diskUtilization()` | 只要 `['disk']` | **守护的独立采样**（后台长期跑，不该让 NAS 每次把六段都算一遍） |

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `read_byte` | 聚合读速率 | B/s |
| `write_byte` | 聚合写速率 | B/s |
| `read_access` / `write_access` | IOPS | 次/s |
| `utilization` | 磁盘忙碌占比 | % |

首页磁盘卡、资源监控页读的就是这几个字段，**不需要新接口、不需要新依赖**。

### 1.2 触发规则（默认值）

```
周期 P = 首页监控档位间隔，下限 2 秒            // 档位见 §2.1；0/1 秒档换算成 2 秒
样本   = 一次轮询拿到的 disk.total
越线   = read_byte ≥ T 且 write_byte ≥ T         // T 默认 40 MB/s，读写「同时」才算
触发   = 连续 2 个越线样本                        // 30s 档 ⇒ 最坏约 1 分钟判定出来
事件结束 = 连续 2 个样本 read_byte 与 write_byte 都 < T/2   // 与触发对称，同样按样本数
冷却   = 事件结束后 10 分钟内不再报第二次（墙钟）
```

四条刻意的取舍：

1. **读写同时越线**才报。备份/下载这类正常负载通常是单向的（要么读要么写），
   勒索加密要读原文件再写密文，是双向同时打满。这一条是误报抑制的主力。
2. **连续 2 个样本**而不是 1 个。单个毛刺（缩略图重建、fsck、快照）很常见。
3. **判定单位是「样本」而不是「秒」**。好处是负担完全由用户自己选的监控频率决定，
   守护不会把 App 变成一个 2 秒轮询机器；代价是慢档发现得晚，见 §2.1 的提示方案。
4. **冷却按「事件」而不是按时间片**。持续高写入 1 小时只报一次，避免刷屏；
   但事件真的结束再复发，会重新报。冷却是系统自动的，「忽略」是你手动按的，两回事。

### 1.3 加强判据（可选，默认关）

`utilization ≥ 90%` 且 `write_access` 明显高于基线时，把阈值 T 自动降到 0.7T。
好处是对「低吞吐高 IOPS 的小文件加密」也敏感；代价是误报上升，所以默认关，
设置页里作为「灵敏模式」。

### 1.4 采样中断本身就是信号

> **【26.11.01 反馈第 1 条：本节的通知部分已取消，只剩日志计数】**
> 「连续失败 → 报失联」和「重新采到 → 报恢复采样」这两条都不再产生通知与消息中心记录，
> 原因是网络误报太多（换网、NAS 短暂不可达都会连续失败），而用户只想看
> **取到的数据有没有异常**。下面这一段保留的是当初的推理，`missedStreak`
> 现在只进 `AppLogger`；代码里对应的删除点在
> `lib/core/disk_watch_rule.dart`（`_onMissed` 恒返回 `none`）与
> `lib/core/disk_watch_service.dart`（`_onLostContact` 已移除）。

**连续 6 个周期**请求失败或拿不到 `data.disk.total` → 报一条
「**守护已失联：无法读取 NAS 磁盘状态**」（默认 4 秒档 ≈ 24 秒；30 秒档 ≈ 3 分钟）。
攻击者停服务、删套件、让 DSM 无响应时，这条比速率报警更早触发。
同理，样本时间戳倒退（NAS 侧时间同步异常）也记一条。

两个必要的限定：

- **忽略（暂停）期间不累计失败次数**，也不允许这条告警发出——否则每次点「忽略」都会
  立刻换一条「失联」通知，等于没忽略。恢复采样时把失败计数清零。
- 6 次而不是 12 次：按秒算的旧写法（12 次 ≈ 24 秒）在慢档下会变成几十分钟才报失联，
  失去意义；改成按周期数走，各档位的「容忍时长」不同，但「容忍次数」一致。

### 1.5 忽略（暂停守护）

报警通知上四个动作按钮，设置页里也有同一组下拉：

```
忽略 5 分钟 / 忽略 15 分钟 / 忽略 1 小时 / 忽略 1 天
```

语义（**是真停轮询，不是只压通知**）：

| 项 | 规则 |
| --- | --- |
| 动作 | 取消 Dart 侧定时器；这段时间内**不发任何请求** |
| 计时 | 墙钟：记 `snooze_until` = 到期时刻（毫秒），不是「剩余周期数」——用户中途改档位不能拉长或缩短忽略时长 |
| 常驻通知 | 文案改成「守护已暂停 · 剩余 14 分钟」，不撤（撤了用户会以为守护死了） |
| 判定位 | 清空「连续越线计数」和当前事件状态。否则 30 秒档下忽略 5 分钟，恢复后第一个越线样本就凑满 2 个立刻再报 |
| 失联判定 | 期间不累计（失败计数只进日志；26.11.01 起已无失联通知，见 §1.4） |
| 重复点 | 后一次覆盖前一次（「从现在起 5 分钟」，不累加）；同一时刻只有一个忽略生效 |
| 到点恢复 | 立即采一次，不等一个完整周期（30 秒档 + 忽略 1 天时，白等一个周期很伤） |
| 进程被杀 | `snooze_until` 落在原生侧（见 §2.3），下次启动读回来继续暂停；已过期则直接恢复 |
| 再犯 | 忽略到期后若再次越线，走完整判定并**重新报警**——已经给过一次机会，不再自动加冷却 |
| 手动恢复 | 设置页那行「守护暂停中 · 剩余 xx」点一下即恢复，不用等 |

第一期就这四档，不做自定义分钟数：四个按钮在通知上要一眼能点，文案长短得受着。

## 2. 轮询与常驻

### 2.1 周期从哪来（本轮核心改动）

**守护复用首页「设备监控」的轮询档位**，不再自己排一个 2 秒定时器。

项目里现成的档位定义（`lib/utils/app_preferences.dart`）：

```
monitorLevels = [0, 1, 2, 4, 8, 16, 30]（秒），默认索引 3 ⇒ **4 秒**
0 档 = 即时（请求一回来就发下一轮，失败时最小间隔 1 秒）
```

> 26.11.01 核对代码时改过一次这里：`defaultMonitorLevel = monitorLevels.length ~/ 2 = 3`，
> 而 `monitorLevels[3]` 是 **4**、不是 8。这一版早期几处文案（含试装包说明）把默认档写成 8 秒，
> 是按索引 4 读的，属于笔误。守护的下限 2 秒、慢档提示 ≥16 秒这两条判定不受影响。

`NotifyService` 已经是这个写法（注释原话：轮询频率直接复用 `keyHomeMonitorLevel`，
同一个滑块控制两处，串行轮询），守护照这个模式接第三条即可，滑块一改动三边同步。

守护侧的两点特殊性：

- **有效周期 P = max(档位间隔, 2 秒)**。0/1 秒档是给人盯着首页看的，
  守护长期跑在即时档就退化成本次要避免的 30 请求/分钟。
- **单份采样、多处消费**：`DiskWatchService` 持有 20 点环形缓冲，
  首页磁盘曲线订阅同一份数据，两处都不再各自发请求。
  首页不可见（切 Tab / 被相册盖住）时守护**继续跑**（这是和 `NotifyService`
  唯一不同的地方——`NotifyService` 那时会停，因为它只为红点服务）。

慢档的代价要说清楚并给出路，但不强制：

| 档位 | 判定最坏耗时 | 每小时请求 | 环形缓冲覆盖 |
| --- | --- | --- | --- |
| 2 秒 | ≈ 4 秒 | 1800 | 40 秒 |
| 4 秒（默认档） | ≈ 8 秒 | 900 | 80 秒 |
| 8 秒 | ≈ 16 秒 | 450 | 160 秒 |
| 16 秒 | ≈ 32 秒 | 225 | 320 秒 |
| 30 秒 | ≈ 1 分钟 | 120 | 10 分钟 |

- 开启守护时若档位是 16/30 秒，卡片上出现一行提示：「当前监控 30 秒一档，异常最快 1 分钟后才报；
  想更快发现就把首页频率调到 2～8 秒」。只提示、不弹窗、不自动改用户的档位
  （代码里是 `DiskWatchService.slowLevelWarn = monitorLevelSec >= 16`）。
- 环形缓冲 20 点在高精度档只有 40 秒窗口，首页曲线的「刚才那波是什么」跨度会随档位变化，
  曲线横轴要显示真实时间而不是点序。

### 2.2 后台（要常驻）

**方案：原生侧只做保活，轮询仍在 Dart。**

- Java 侧新增一个真正的 Android `Service`（当前工程里
  `DownloadManagerService.java` 只是 `DownloadManager` 的包装类，不是系统 Service；
  manifest 里唯一的真 Service 是 `audio_service` 插件的 `AudioService`），
  `startForeground()` + 一条低优先级常驻通知；
- Dart 的 `Timer` 在进程存活期间继续跑（Flutter 侧实测行为：Dart Timer 在后台会降频，
  但前台服务能把进程保在系统豁免名单内）。

为什么不选「原生侧自己发 HTTP」：那必须把 `_sid` / `X-SYNO-TOKEN` 下发到原生，
绕开项目现有的网络参数保护层级（FFI + 原生 .so 那套），等于把凭据放在更弱的地方。
保活方案不需要交出任何凭据。

**本期只做 Android。** iOS 没有对等的后台常驻；用 `audio_service` 那套媒体会话保活来跑磁盘守护
属于滥用（会占住锁屏播放控件），不做。iOS 侧退化为「App 在前台 / 未被系统挂起时守护」。

### 2.3 通知

两个 channel，别混用：

| channel | 优先级 | 内容 |
| --- | --- | --- |
| `watch_ongoing` | LOW，无声音、不可横幅 | 「守护运行中 · 最近采样 读 1.1 KB/s · 写 104.8 KB/s」，点击进首页磁盘卡；忽略期间显示「守护已暂停 · 剩余 14 分钟」 |
| `watch_alert` | HIGH，横幅 + 声音 | 「磁盘读写异常：连续 2 次超过阈值」+ 峰值与当前值 + 四个动作按钮「忽略5分钟」「忽略15分钟」「忽略1小时」「忽略1天」，点击正文进首页磁盘卡 |

**通知暂时不走第三方库**：项目现在没有 `flutter_local_notifications`（已核 pubspec 与 lock，
`audio_service` 也不带它）。这条结论的完整对比——它到底比自写原生多给你什么、多花多少包体积——
写在 **§8**，那里是实测数字，不是估的。看完 §8 你再拍；在那之前按自写路线设计：
通知由我们自己那个 Java Service 用框架 API（`NotificationManagerCompat` + `NotificationChannel`）发，
动作按钮用 `Notification.Action` + `PendingIntent.getBroadcast` 回到我们的接收器。

这里有个必须提前想清楚的坑：工程里现有的 `DownloadBroadcastReceiver` 是**动态注册**的
（`onReceive` 里靠 `EventChannel.EventSink` 回 Dart），要求 Flutter 引擎还活着。
通知按钮恰恰常在引擎已死时被点。所以：

- 新增一个 **manifest 静态注册**的接收器（拟名 `GuardActionReceiver`），
  它只做一件事——把 `snooze_until` 写进**原生侧 SharedPreferences**，再更新常驻通知文案；
- Dart 侧通过 MethodChannel 读写同一个键（`getSnoozeUntil` / `setSnoozeUntil`），
  以原生那一份为准。**不要**让接收器去猜 `shared_preferences` 插件的内部文件名，
  那是插件实现细节，升级会变。

清单侧现状（已核实）：`POST_NOTIFICATIONS`、`WAKE_LOCK`、`FOREGROUND_SERVICE` 已声明；
`FOREGROUND_SERVICE_MEDIA_PLAYBACK` 已声明（audio_service 用）。新增服务需要
再补一个类型权限 —— Android 14(API 34) 起前台服务必须显式声明 `foregroundServiceType`，
`dataSync` 有累计时长限制，本场景更适合 `specialUse`（我们自己分发 APK，
不需要走商店的用途审核）。这一段要在真机上验证，不能只按文档写。

### 2.4 成本与诚实的局限

- 按默认 4 秒档算 ≈ 15 请求/分钟（这是首页不可见、守护自己发请求的上限；首页在跑时那份样本是白拿的，守护一个请求都不发），30 秒档 ≈ 2 请求/分钟；
  旧的「固定 2 秒」方案是 30 请求/分钟——**改成跟随档位，负担下降一个数量级**，
  这就是你要的那条理由。**具体电量影响仍未实测**，实现后要拿一台机器跑 1 小时看掉电曲线。
- 慢档换低负担的代价是发现得晚：30 秒档最坏 1 分钟，而加密 1 分钟能过掉不少文件。
  这个取舍由用户用滑块自己决定，守护只负责把话说明白（§2.1）。
- 前台服务**不等于杀不死**。国产 ROM 的省电策略、用户手动强停、系统重启后都不会自动恢复。
  所以设置页必须有一行「守护状态：上次采样 xx 秒前」，让用户能看出它是不是真的活着；
  并在被杀后由 App 下次启动时自动 `startForegroundService` 拉起。
- 真正 7×24 可靠的检测应该跑在 NAS 侧（DSM 计划任务 + 本地脚本），手机侧守护是补充。
  需要的话可以另出一份 NAS 侧脚本方案，但那是另一件事。

## 3. 与首页 / 消息中心的联动

- 报警同时写入本地消息列表 → 铃铛未读数 +1（未读水位机制见首页方案）。
- 首页磁盘曲线画出**红色阈值线**，越线的点标红，用户点进去能看到「刚才那波是什么」。
  但阈值线不能硬画：**纵轴跟着样本峰值走**（轴上限 = 峰值 × 1.1），只有 `阈值 ≤ 轴上限` 时
  才把虚线画进图里，否则在右上角标一行「阈值 40 MB/s · 当前量程外」。
  平时读写只有 KB/s，把 40 MB/s 的线画进来会把曲线压成贴底的一条直线，反而什么都看不见。
  真报警时轴自动放大到包含阈值，红线与红点一起出现。
- 传输页有活跃任务时，报警文案追加一行「当前有 2 个传输任务在进行，可能是正常写入」，
  **只做提示、不做静默**：中毒时用户完全可能同时在下载东西。
- 忽略状态在首页守护 pill 上也要看得见（「守护暂停 14 分钟」），
  避免用户在首页盯着曲线却以为守护还在判。

## 4. 设置项（我的 → 安全与隐私）

| 项 | 默认 | 可选 |
| --- | --- | --- |
| 开启守护 | 关 | 开/关 |
| 触发阈值 | **40 MB/s** | 可调：10 / 20 / 40 / 60 / 80 / 120 MB/s 档位（默认停在 40），改完下一个样本就生效 |
| 采样间隔 | **跟随首页监控档位**（默认 4 秒，守护下限 2 秒） | 不给独立选项，滑块在首页；这里只显示当前有效周期 |
| 忽略中 | — | 「守护暂停中 · 剩余 xx」+「立即恢复」；主动暂停可选 5 分钟 / 15 分钟 / 1 小时 / 1 天 |
| 灵敏模式 | 关 | 用忙碌率与小文件特征降低有效阈值 |
| 进程处置 | 关 | 开/关；开启前要过一次「NAS 侧一次性授权设置」（见 §7） |

**没有「后台常驻」这一项**（26.10.31 你定的）：开守护 = 前台服务 + 那条 LOW 常驻通知一起上，
关掉守护 = 三者一起没。不再单独给一个开关，免得出现「守护开着但通知被自己关掉」这种说不清的状态。

通知权限未授予时，卡片顶部出现一条内联提示 + 「去开启」按钮（Android 13+ 需要运行时授权），
而不是等用户收不到通知再困惑。

## 7. 手机侧处置可疑进程（暂停 / 杀掉）——可行性调研

你问的是：能不能在 App 里选中一个可疑进程，直接**暂停**（对应 `kill -STOP`）或**杀掉**
（对应 `kill -9`），单选就够。这是终端命令，所以先把「App 手上有什么牌」摊开说。

### 7.1 我们现在真正验证过能用的牌

| 能力 | 接口 | 状态 |
| --- | --- | --- |
| 列出进程（pid / 名字 / 属主 / CPU / 内存） | `SYNO.Core.System.Process` `method:list` | **已实测**，资源监控页在用（`lib/pages/home/resource_monitor_page.dart:92`） |
| 列出进程组 / 套件服务 | `SYNO.Core.System.ProcessGroup` | 已封装 |
| 列出任务计划、启用/禁用、**立即运行一条脚本型任务** | `SYNO.Core.TaskScheduler` `list` / `set_enable` / `run` | **已实测**，任务计划页在用（`task_scheduler_page.dart:90`，`type=='script'` 走 `taskRun([id])`） |
| 往共享目录写一个文件 | `SYNO.FileStation.Upload` `method:upload` | 已实测（`dsm_api.dart:947`） |
| 停整个套件 | `SYNO.Core.Package.Control` | 代码里有 `launchPackage(...)`，但 **`start` 分支传参形态我确认过，`stop` 分支没实测** |

**没有的牌**：`SYNO.Core.System.Process` 在我见过的形态里只有 `list`，**DSM 没有给 App 一个
「杀掉 pid」的官方接口**，我也没在你机器上找到过。所以「暂停/杀掉」必然要借一条能执行命令的通道。

### 7.2 四条路线与取舍

**路线 A：SSH 直连执行 `kill`**（最直观，但我不建议）
- 要引 `dartssh2`（违反零新增依赖），要在 App 里存 NAS 口令（这台机器刚被勒索过，
  再多存一份可用凭据是净增风险），还依赖用户在 DSM 上开着 SSH 终端。
- 按我们的安全约束，口令不进命令行、不进脚本，只能进加密存储 + 每次现取，工程量全在安全侧。
- **判定：本期不做。**

**路线 B：只停「套件」，不停任意进程**（最稳，粒度粗）
- 场景对得上一大半：真正能持续高读写的常见是某套件的活儿（索引、下载、Docker、备份任务）。
- 用已封装的 `SYNO.Core.Package.Control`。它的好处正是**粒度粗到不会把系统搞挂**：
  停一个套件不会伤到 DSM 本体，手动 start 回来即可。
- 代价：要先实测 `stop` 分支参数；杀不掉非套件的野进程（勒索类二进制恰恰不是套件）。
- **判定：值得先做，作为「一键止血」。**约 0.4 人日。

**路线 C：预建一条 root 任务计划 + App 写指令文件**（能做「任意进程」，且不引依赖、不开 SSH）
思路是把「执行权」留在 NAS 侧、App 只填参数：
1. **一次性授权设置**（App 里给图文步骤，用户在 DSM「任务计划」手工建一条）：
   类型为「自定义脚本」、**以 root 身份运行**、触发方式「手动/按需」，脚本内容固定为一段
   读指令文件并按白名单执行的小脚本（我们提供原文，用户复制粘贴）。
2. **App 侧每次处置**：用已实测的 `FileStation.Upload` 往一个只有 admin 可写的固定路径写一行
   `stop <pid>` / `cont <pid>` / `kill <pid>`（pid 只接受整数，Dart 不做任何 shell 字符串拼接），
   紧接着调已实测的 `taskRun(taskId)` 触发那条任务，root 去执行，执行完脚本自删指令文件。
3. App 记下这条任务的 id（从 `taskScheduler()` 列表里按我们约定的任务名前缀找到），
   设置页显示「处置能力：已授权 / 未授权」，未授权时按钮置灰并给图文入口。
- 优点：零新依赖、不开 SSH、不存口令，走的认证链就是我们天天在用的 session + SynoToken。
- 代价：**必须用户手工建一次任务**（这是硬门槛）；执行有秒级延迟；
  「创建任务」的 API（`method:set`/`create` 与 `as_root`/`cmd` 等字段）**我没有实测过**，
  能不能做成全自动引导，要先抓一次 DSM 网页端「新增自定义脚本任务」的请求才知道。
- **判定：这是唯一能在纯 App 端做出「暂停/杀掉任意进程」的现实路线**，约 2.2 人日（含进程页 UI 0.7）。

**路线 D：NAS 侧常驻 helper（自建服务收处置指令）**
最干净（白名单、审计、无脚本落盘），但要装东西、占端口。你说过「之前的服务不要管」，
所以列为长期项，不做。

### 7.3 不管走哪条路线都必须装的护栏

进程处置是这个功能里唯一会**改变 NAS 运行状态**的动作，比报警本身危险得多：

1. **保护名单**：pid 1 与 DSM 核心服务（`synoscgi`、`sshd`、`pkgmgr`、samba、nginx、数据库等）
   一律置灰不可选。名单不能我拍脑袋写，要拿一次真机 `Process list` 采样，把实际进程名整理出来再定。
2. **单选**（你说不要多选），且「暂停」和「杀掉」是两个明确按钮，不做默认动作。
3. **高危二次确认**（按项目既有规范）：确认层要显示 pid、属主、完整命令行、CPU/内存、
   以及「它现在贡献了多少读写」，并要用户**输入 pid 后三位**才能提交——不是只点一下「确定」。
4. **默认引导用「暂停」不用「杀掉」**：`SIGSTOP` 冻结进程但保留内存与打开的文件描述符，
   既能立刻止血，又留了现场（上次那种事件里这就是取证材料），还能 `cont` 撤销；
   `SIGKILL` 不可撤销，且**被 DSM 守护的关键服务会被自动重新拉起**——用户点了「杀」却发现它还在，
   这种体验必须提前在文案里说明白：这类进程请改用「停套件」或去 DSM 任务计划里禁用。
5. **处置后回采**：3 秒后重新拉一次进程列表，把「还在不在 / 是否已进入 T(停止) 状态」显示出来，
   失败要给原因，不能只弹个「已发送」。这里有个必须先核的事实：
   `Process list` 返回里**有没有表示进程状态的字段（state/S/T）我还没实测过**，
   我们现在的进程页只用了 pid、名字、cpu、mem。实现时要先真机采一次表看字段；
   若确实没有状态字段，「已暂停」就只能靠间接证据显示（CPU 掉到 0、守护读数跟着掉下来），
   文案要老实写成「疑似已暂停」而不是「已暂停」。
6. **可撤销**：App 里维护一份「本机暂停过的 pid」清单（存 `AppPreferences`），
   给一个「恢复」入口；重启 App 也要看得见，避免用户把某个进程冻在那儿自己忘了。
   顺带一个硬限制：**pid 会随重启失效**，所以「恢复」只对当次开机周期有意义，
   清单里要带上启动时间或在回采时校验同 pid 是否还是同一个进程（按名字比对），
   否则可能出现「恢复」按钮把新起的无关进程 CONT 一下的尴尬。
7. **通知栏不给处置按钮**。报警通知只有忽略四档；处置只在 App 内、登录后、admin 身份下可用，
   并且要过指纹/应用锁（应用锁已经做了）。误触一条通知就杀进程，代价太大。
8. **本地审计**：每次处置写 `AppLogger` 与一条本地事件（时间、pid、命令、结果），
   消息中心可见，便于事后回看「我什么时候停了什么」。
9. **路线 C 的指令文件等于开了一个 root 执行口，必须把口子焊死**：
   NAS 侧那段脚本只能接受极窄的格式（整行匹配 `^(stop|cont|kill) [0-9]{1,7}$`，
   不匹配就直接丢弃并留一行日志），**任何情况下都不许把文件内容原样交给 shell**；
   pid 要先在脚本里对照进程表确认存在、且不在保护名单内才动手。
   Dart 侧同样不允许出现 shell 字符串拼接，只写整数。
   这条不是洁癖：这个文件谁能写，谁就拥有了这台 NAS 的 root 执行能力。

### 7.4 我建议的落地顺序

1. 先做守护报警本体（§5 的 1–7 步），这是价值主体；
2. 再加「一键停套件」（路线 B，0.4 人日，接口现成）；
3. 进程页（已存在的资源监控进程列表）加单选 + 处置按钮 UI，先接路线 B；
4. 想上「任意进程暂停/杀掉」再做路线 C：先在实机抓一次 DSM 新增脚本任务的请求，
   确认能不能由 App 自动创建；能则做全自动引导，不能则做图文一次性授权。

## 8. 通知：加 `flutter_local_notifications` vs 自写原生

### 8.1 先把「库到底替我们干了哪一层」说清楚

这个功能有两块活，库只覆盖其中一块：

| 活 | 谁做 | 说明 |
| --- | --- | --- |
| 后台常驻的前台服务本体（Service、manifest、`foregroundServiceType`、被杀后拉起、Android 13+ 通知授权） | **无论加不加库都得我们自己写** | 库不负责创建/管理 Android Service，这块是守护能不能活着的关键 |
| 通知的展示层（channel、优先级、横幅、动作按钮、更新/取消文案） | 库给封装 / 或自己用 `NotificationCompat` 写 | 自写量级：一个 helper 类 + channel 初始化，约 150 行 Java |

### 8.2 能力与体验对比

| 维度 | 库 | 自写原生 | 对我们的影响 |
| --- | --- | --- | --- |
| 用户看到的观感 | 同一套系统 API 出来的 | 同一套系统 API 出来的 | **无差别**。channel/优先级做对了就一样 |
| 动作按钮在**引擎已被杀**时还能生效 | 回调最终仍要回 Dart，引擎死了照样收不到 | 我们的 `GuardActionReceiver` 直接写原生 prefs | **库帮不上这个最要紧的场景**，§2.3 的设计照旧 |
| iOS 端 | 现成（含权限请求） | 要再写一套 ObjC/Swift | 本期只做 Android（§2.2），用不上；**以后 iOS 要做守护时这是库最大的价值** |
| 定时/周期通知 | 现成（还要额外初始化 `timezone`） | 自己接 `AlarmManager` | 守护是事件驱动，不需要定时通知，用不上 |
| 富样式（大图、分组、角标数） | 封装好 | 也能做，但要自己踩每个 API level 的细节 | 我们只用正文 + 4 个按钮 + LOW 常驻，用不上 |
| 维护 | 跟着 Android 通知策略变（近两年变更多），升级要跟版本 | 只依赖框架稳定 API | 自写的维护成本更低，但踩坑也更多 |
| 依赖面 | **一次拉进 6 个包**：主库 + platform_interface + linux/windows/web 三平台实现 + `timezone` | 0 | 与零新增依赖策略冲突，需要你批例外 |

### 8.3 包体积（实测）

方法：同一份工作区源码，只改依赖，各打一个 arm64 release 包（`flutter build apk --release
--target-platform android-arm64`），再按 APK 内条目对比。测完所有临时改动已回滚，
回滚后重打的包与基线**字节数完全一致**（44,908,419 B），确认没留手尾。

| 构建 | APK 字节 | 相对基线 |
| --- | --- | --- |
| 基线（无库） | 44,908,419（42.8 MiB / Flutter 报 44.9 MB） | — |
| 加库 + 打开 core library desugaring | 45,076,789 | **+168,370 B ≈ +164 KB（+0.37%）** |
| 只加库、不动 desugaring | **构建失败**：AGP 要求先开 desugaring | — |

多出来的 164 KB 具体在哪（按 APK 内条目拆，压缩后 / 未压缩）：

| 条目 | 差值 | 装的是什么（在 dex 里按包名串验过） |
| --- | --- | --- |
| `classes.dex` | +79,132 / +175,532 | 库自己的 Java（`com/dexterous`）+ `gson` + 零散 `j$` 脱糖类 |
| `classes2.dex` | +92,697 / +204,752 | `desugar_jdk_libs` 的 `j$.*`（java.time 那套），**新多出一个 dex** |
| `resources.arsc` / `AndroidManifest` | +408 / +20 | 可忽略 |
| `lib/arm64-v8a/libapp.so`（Dart AOT） | **+0（字节数完全没变）** | 见下面这条说明 |

有一条必须说清楚，不然这个数字会骗人：我为了测 Dart 侧开销，在 `main()` 里写了段构造插件对象的探针，
结果 `libapp.so` 一字节没涨——三个包的 `libapp.so` 大小完全相同、只有 CRC 不同，
说明那段赋值没被任何地方读取，**被 AOT 当死代码消掉了**。
所以 **+164 KB 是「Java 侧」的净增量，不含真正接入后的 Dart 代码量**。
不过这一项对结论没影响：自写方案同样要写一层 Dart 侧的 MethodChannel 封装与通知模型类，
两边在 Dart 这块基本对等，真正只有「加库」才多出来的就是上面那 164 KB。

另外两条实测到的连带成本，比体积更值得在意：

1. 这库的 Android 侧声明了 `coreLibraryDesugaring desugar_jdk_libs:2.1.4`，而我们的工程
   **当前没开脱糖**（`android/app/build.gradle.kts` 里没有该项）。想用它不是加一行 pubspec 就完事，
   得先在 app 模块开脱糖——`compileOptions { isCoreLibraryDesugaringEnabled = true }`
   还得写在 `compileOptions` 里（我先放进 `defaultConfig` 时 AGP 直接编译失败），
   并新增一个顶层 `dependencies { coreLibraryDesugaring(...) }`。
2. Android 侧还带 `androidx.core`、`androidx.media`、`gson`；前两个我们工程里已有别的插件在用（不额外长），
   `gson` 是新面孔——而且我们**没开 R8 收缩**（`buildTypes.release` 只配了 signing，无 `minifyEnabled`），
   所以它的类是整份进 dex 的（实测 `classes.dex` 里能搜到 `com/google/gson`）。
3. 依赖面：`flutter pub add` 一次拉进 **6 个包**——主库、platform_interface、
   linux / windows / web 三个平台的实现、以及 `timezone`。

### 8.4 建议

先纠正一句：**体积不是理由**。实测只多 164 KB（+0.37%），对一个 42.8 MiB 的包来说无所谓，
我原来要是拿「库很大」当论据那是错的。

本期仍建议**自写**，理由按分量排：

1. 这个功能真正麻烦的两块——前台服务本体、以及「引擎已被杀时点通知按钮也要生效」——**库都管不了**，
   照样得我们写原生。它能替掉的只有 `NotificationCompat` 那层薄壳（约 150 行 Java）。
2. 它最强的两点（iOS 现成支持、定时/预约通知）本期都不在范围内（§2.2 已定本期只做 Android）。
3. 用它要顺带打开 core library desugaring、多一个 dex、多 6 个包，这些是**永久性**的，
   而我们只用到它不到两成的能力。

反过来说，什么时候该引它：**要做 iOS 侧守护**，或者出现**预约类通知**需求
（例如每天固定时间报一次 NAS 健康、证书到期提醒）。那时收益配得上成本，我按依赖例外流程申请。

### 9.1.1 交付前那一轮自查抓到并改掉的错（记下来免得再犯）

1. **铃铛数字差点翻倍**。`NotifyService.unreadCount` 内部已经是
   `_dsmUnread + _extraUnread`（守护事件由 `setExtraUnread` 折进 `_extraUnread`），
   首页徽标却又加了一次 `DiskWatchService.unreadEventCount` —— 一条报警会显示成「2」。
   现在只读 `unreadCount` 一个来源，并补了一条单测钉住「进一条报警，徽标 +1 而不是 +2」。
   顺带把监听里的 `DiskWatchService` 从 merge 中去掉：守护每次采样都 notify 一次，
   留着它等于每 2~8 秒白重建一次顶栏。
2. **关守护不该把曲线一起清空**。`setEnabled(false)` 原来会 `ring.clear()`，
   但那份环形缓冲是**首页磁盘曲线的本体**，守护只是它的消费者之一；关掉一个判定开关
   却让用户回到首页看到那张卡空掉，像 App 坏了。现在只停轮询、清忽略，采样数据留着——
   误导不成立是因为阈值线和越线红点在页面上本来就走 `watch.enabled` 门禁，关掉即不标红。
   对应单测的断言也从 `ring.isEmpty` 改成「至少留一个点」。
3. 状态行那侧不受影响：`_statusLine` 在 `!enabled` 时打的是「守护未开启」，
   不会把留着的那个旧采样时间读成「还在采」。
4. **本文与试装说明里的「默认 8 秒」是笔误，实际默认档是 4 秒**（§2.1 已就地更正并留了原因）。
   `AppPreferences.defaultMonitorLevel = monitorLevels.length ~/ 2 = 3`，而
   `monitorLevels[3] = 4`——我当时按索引 4 读成了 8。受影响的是「失联多久才报（≈24 秒）」
   和「每小时多少请求（≈900）」这两条推算，判定与下限逻辑本身没写错。

### 9.2 四件必须真机才能收尾的事

1. **通知按钮那条链**（§2.3）：点「忽略 15 分钟」→ 原生 `snooze_until` 落盘 → Dart 侧看门狗在
   引擎被杀的情况下到点恢复。Dart 那半有单测，原生那半只能装到机器上，把 App 从最近任务里
   划掉再点按钮才算验过。
2. **前台服务在国产 ROM 上到底活多久**（§2.4 那条诚实的局限）：OnePlus/ColorOS 需要实测
   电池优化对白名单的影响，方案里没打算把它说成「一定能常驻」。
3. **档位改动即时生效**：首页滑块 → `restartSchedule()` → pill 上那个「守护中 · X 秒」跟着变。
4. **通知权限被拒的那条路径**（§4 最后一段）：在 Android 13+ 上先把本应用的通知总开关关掉，
   再点「开启守护」——预期是系统运行时授权弹一次，仍不给就停在「需要先允许通知」那个框、
   **守护开关弹回关闭态**（这就是你定的「它不接受就不打开安全防护这个功能」）。
