# 进程处置授权设置（路线 C · 一次性在 NAS 上建 root 通道）

> 对应 App 里的功能：资源监控页 → 进程 → 每行右边的「⋯」→ 暂停 / 恢复 / 杀掉。
> 方案背景与取舍见 `磁盘异常读写守护方案.md` §7；这份文档只管**怎么把通道打开**。
>
> **做一次就长期有效。** 做完之后 App 每次处置只是往一个固定文件里写一行、
> 再触发那条计划任务，不需要再登录、再授权、也没有常驻进程。

## 0. 先看清这意味着什么

打开这个通道之后，**谁能往 `/nasflow_guard/proc_cmd.txt` 里写一行，谁就能让这台 NAS
以 root 身份执行 `kill -STOP / -CONT / -9`**。

所以三条要求不是建议，是前提：

1. 那个共享目录**只给 admin 账号读写**，其他账号一律不给（连"读取"都别给：
   看得到路径就能猜怎么写）。
2. 这个目录**只放这一个指令文件**，不要往里存别的东西，也不要把它分享给别人。
3. 不想要这个能力了就**回去把那条计划任务停用**（控制面板 → 任务计划 → 选中 → 停用），
   这样即使指令文件被人写了也没人去执行它。

App 侧还有一道自己的拦下规则（pid 1、禁止处置名单），但**真正的边界是下面那段脚本**：
脚本按 `/proc/<pid>/exe` 的实际落盘位置判断，系统目录里的进程一律拒绝。

## 1. 建共享文件夹「nasflow_guard」

控制面板 → 共享文件夹 → **新增**：

| 项 | 填什么 |
| --- | --- |
| 名称 | `nasflow_guard` ← **必须一字不差**，App 按这个名字找它 |
| 父路径/位置 | 选你要放的那个大卷（下面假设 `/volume1`） |
| 加密 | **不要勾**（root 脚本按明文路径读） |
| 权限 → 只读 | 把所有人移出去（留空） |
| 权限 → 可读写 | 只加你 App 登录用的那个 admin 账号 |

建好后「共享文件夹」列表里那一行会显示**路径**，形如 `/volume1/nasflow_guard`。
**把这串路径记下来**，第 2 步脚本第一行要用。

App 里那个「怎么看开通步骤」弹窗显示的共享名，就是代码常量 `kProcShareName`；
改了名字就等于没开通（进程页底部那行小字会说「共享文件夹「nasflow_guard」还不存在」）。

## 2. 建 root 计划任务

控制面板 → 任务计划 → **新增 → 任务计划 → 自定义脚本**：

| 页 | 项 | 填什么 |
| --- | --- | --- |
| 常规 | 任务名称 | `NasFlow 进程处置` ← **必须一字不差**（含那个空格），App 靠它找回这条任务 |
| 常规 | 用户账号 | **root** |
| 常规 | 已启用 | 勾上 |
| 设置 | 计划类型 | 选「每天」，时间随便（这一条**不靠排期工作**；真正的执行由 App 手动触发）。别选「不开启」，有些 DSM 版本里未启用的任务不能手动触发 |
| 设置 | 「将任务保留在列队中，即使它已经错过开始时间」 | 不勾 |
| 计划 | （若有「在系统启动时」） | 不勾 |
| 第 2 步 | 正文 | **整段替换成下面那段脚本** |

### 脚本正文（整段复制，只改第一行的路径）

```sh
SHARE_DIR="/volume1/nasflow_guard"   # ← 只改这一行：改成第 1 步里显示的那串路径

# NasFlow 进程处置 · 执行端。
#
# 只做四件事：读那一行 → 判该不该执行 → 执行 → 把文件删掉。
# 任何时候都不把文件内容原样交给 shell：它先过整行白名单，再只取两个字段。
# BusyBox ash 写法（黑群晖上没有 bash 的 pgrep/[[ ]] 那些东西，这里只用最基础的）。

CMD_FILE="$SHARE_DIR/proc_cmd.txt"
LOG="$SHARE_DIR/proc_exec.log"

log() {
    printf '%s %s\n' "$(date +%Y-%m-%dT%H:%M:%S)" "$1" >> "$LOG" 2>/dev/null
}

# 0) 没有指令文件就什么都不做（这条任务被排期自己跑到时就会走到这里）
[ -f "$CMD_FILE" ] || exit 0

LINE=$(head -n 1 "$CMD_FILE")

# 1) 整行白名单：只认 "<动作> <1~7 位数字>"，和 App 侧用的是同一个式子。
#    对不上就丢弃 + 删文件，绝不猜测用户想干什么。
printf '%s' "$LINE" | grep -Eq '^(stop|cont|kill) [0-9]{1,7}$'
if [ $? -ne 0 ]; then
    log "REJECT_FORMAT 内容不符白名单，已丢弃"
    rm -f "$CMD_FILE"
    exit 0
fi

ACT=${LINE%% *}
PID=${LINE##* }

# 2) 这个 pid 真的存在吗
if [ ! -d "/proc/$PID" ]; then
    log "SKIP $ACT $PID 进程不在了"
    rm -f "$CMD_FILE"
    exit 0
fi

# 3) 保护：pid 1、本脚本自己和它的父进程，一律不动
if [ "$PID" = "1" ] || [ "$PID" = "$$" ] || [ "$PID" = "$PPID" ]; then
    log "DENY $ACT $PID 是 init 或本次执行自己"
    rm -f "$CMD_FILE"
    exit 0
fi

# 4) 真正的边界：按可执行文件的落盘位置判，系统目录里的进程一律拒绝。
#    内核线程的 exe 链接是空的，也一并落进这个拒绝里。
EXE=$(readlink "/proc/$PID/exe" 2>/dev/null)
case "$EXE" in
    ""|/bin/*|/sbin/*|/usr/bin/*|/usr/sbin/*|/usr/lib/*|/usr/libexec/*|/lib/*|/usr/local/bin/*|/usr/syno/*|/init/*)
        log "DENY $ACT $PID exe=[$EXE] 在系统目录或读不到"
        rm -f "$CMD_FILE"
        exit 0
        ;;
esac

NAME=$(cat "/proc/$PID/comm" 2>/dev/null)

# 5) 执行。三条分支各对应一个信号，不做任何拼接。
case "$ACT" in
    stop) kill -STOP "$PID" ;;
    cont) kill -CONT "$PID" ;;
    kill) kill -9 "$PID" ;;
esac

# 6) 立刻回看一眼实际状态（/proc/<pid>/stat 第 3 个字段是任务状态字母：
#    T=被冻住，R/S/D=还在跑；进程没了就读不到）。把证据写进日志，
#    App 那边显示「已暂停 / 仍在运行」用的也是这套判据。
sleep 1
STATE=$(cut -d' ' -f3 "/proc/$PID/stat" 2>/dev/null)
if [ -z "$STATE" ]; then
    log "DONE $ACT $PID $NAME 已结束（/proc 里没有了）"
elif [ "$STATE" = "T" ]; then
    log "DONE $ACT $PID $NAME 状态=T 已冻住"
else
    log "DONE $ACT $PID $NAME 状态=$STATE 仍在运行"
fi

# 7) 指令文件读完就删：一次指令一次生效，不留给下一次排期重复执行
rm -f "$CMD_FILE"
exit 0
```

保存后：

1. 选中这条任务 → **执行一次** → 没报错（此时共享目录里还没有指令文件，脚本应当
   静默退出，什么都不会发生）。
2. 打开共享文件夹，应该**没有** `proc_exec.log`（因为第 0 步就退出了，还没写过日志）——
   这是正常的。第一次真正处置之后它才会出现。

## 3. 哪些进程一定动不了（这段脚本自己拒的）

这几类点在 App 里也会「发出去了但仍在运行」，因为脚本那关就没过 —— 这是刻意的保守，
不是 bug：

- **pid 1**、这条任务自己（以及它的父进程）；
- **内核线程**：`/proc/<pid>/exe` 读不到东西；
- **落在系统目录里的进程**：`/bin`、`/sbin`、`/usr/bin`、`/usr/sbin`、`/usr/lib`、
  `/usr/libexec`、`/lib`、`/usr/local/bin`、`/usr/syno`、`/init`。DSM 自己的服务
  （synoscgi、Samba、 NFS、套件守护进程等）基本都在这里，杀掉会让面板或共享挂掉，
  而且会被守护立刻拉起 —— 那种「我杀了它它又回来了」的现象本来就不该用这个功能解决，
  要停套件请去套件中心点「停用」。
- **装在容器里的进程**（Docker）：它们的 exe 路径常常也是 `/usr/bin/…`，
  会被上面那条规则一起拒掉。**要停容器就去 Docker 页面停容器**，别用这里。

想放宽就在脚本那个 `case` 里改（少一条前缀就多一分危险），改完 App 侧不用动。

## 4. 让 App 认到这条通道

App 的进程页会在你点进「进程」段时自动查一次（两个请求：任务列表 + 共享列表）。
判定规则写死在代码里：任务名 = `NasFlow 进程处置`、类型 = 自定义脚本、未停用，
共享名 = `nasflow_guard`。三者都齐，进程行右边的「⋯」才会给出暂停/恢复/杀掉。

查不到时进程列表底部会显示那行缺的东西。常见三种：

| 界面说的话 | 实际原因 |
| --- | --- |
| NAS 上还没建那条 root 任务「NasFlow 进程处置」 | 名字打错了 / 建成了「备份」类型 / 任务被停用 |
| 共享文件夹「nasflow_guard」还不存在 | 名字打错了，或当前账号看不到它（权限没给到） |
| 没查到授权状态：… | 登录态掉了或账号没有读这两张表的权限，重新登录再看 |

## 5. 用起来是什么样

进程页每行右边一个「⋯」（和文件页同一个位置、同一个图标）。点开能看到
**暂停（可恢复）／恢复它／杀掉（不可撤销）**，选完要**手输 PID 的后三位**才发出去
——这一条是为了挡手滑点错行，不是走形式。

发出去之后 App 等 3 秒，重新取一次进程表来确认，然后照实说：

| App 显示的 | 意思 |
| --- | --- |
| 已结束：这个 pid 已经不在进程表里了 | 杀掉生效了 |
| 已暂停：回采到它的状态是 T（被 SIGSTOP 冻住） | 暂停生效了 |
| 已恢复：进程还在，状态不再是 T | 恢复生效了 |
| 仍在运行：指令没被执行，或它被 DSM 守护重新拉起了 | **点了不等于成了**，去看 `proc_exec.log` |
| 已发出，未能确认：回采没拿到这个进程的状态字段 | 进程表这一轮没回状态，别当成已生效 |
| 没发出去：指令文件没写成，或找不到那条计划任务 | 通道没通，共享/任务/权限三者之一 |

每一笔都记在手机本地（只存本机，最近 30 条），入口是同一个面板里的
「处置记录（N）」。里面还会列出「你暂停过、后来没恢复也没杀掉的进程」——
它们会一直冻着直到恢复或重启机器。

## 6. 还没在真机上核实过的两件事

实现时按「拿不到证据就说不确定」写的，所以以下两条不影响安全，只影响话术：

1. **DSM 进程表有没有状态字段**：App 侧回采读的是 `status`（抓包里 `SYNO.Core.System.Process`
   确实有这一项，值形如 `S`/`R`）。`T` 这一档在这台机器上还没实测过，第一次真机暂停之后
   看它是不是显示「已暂停」就能定案。
2. **任务名和 `type` 字段的实际取值**：不同 DSM 版本里自定义脚本任务的 `type` 字符串
   若不是 `'script'`，App 会认不到那条任务（会明说「还没建」）。真遇到就在
   日志中心看 `taskScheduler` 那条回包里的键值，我再按实际值改判据。

如果第 4 步 App 一直说找不到任务，先用抓包/日志中心确认那条任务回的 `name` 和 `type`，
不要为了「让它通过」把脚本改成别的类型。

## 7. 撤销这个通道

任一即可，第 1 种最彻底：

1. 控制面板 → 任务计划 → `NasFlow 进程处置` → **停用**（或先停用、确认 App 侧行为变了再删除）。
2. 删掉共享文件夹 `nasflow_guard`（App 会立刻显示「共享文件夹还不存在」）。
3. 顺手把 `proc_cmd.txt` 删掉：里面若留着最后一行指令，下次触发时会执行它一次
   —— 正常流程是脚本执行完就自删，所以有残留说明那次执行没跑成。
